## 4. 단계별 수정 계획

### Stage A — 기준선 보존과 범위 동결

1. 보호 파일 3개의 SHA-256, 크기, 수정 시각을 수정 전 기록한다.
2. 현재 Step 3 원시 JSON과 캡처를 덮어쓰지 않고 보존한다.
3. 슬림 레일·2D 모드·호버 카드 등 범위 밖 기능은 추가 확장하지 않는다.
4. 범위 밖 기능은 이번 수정에서 임의 삭제하지 않고 회귀 검증 대상으로만 유지한다.

완료 조건: 수정 전 기준선 JSON과 보호 파일 해시가 별도 기록되어야 한다.

### Stage B — 모바일 필터 44px 및 2행 구조 수정

1. `768px` 이하에서 필터를 명확한 2행으로 배치한다.
   - 1행: 시도, 시군구, 공정위 연도, 공정위 패널 버튼
   - 2행: 8대 업종과 `CAT_MAJ_99` 가로 스크롤
2. `select`, 업종 탭, 공정위 버튼의 실제 `getBoundingClientRect()` 높이와 폭을 각각 최소 44 CSS px로 맞춘다.
3. 390px 화면에서 문서 가로 오버플로를 0px로 유지한다.
4. 첫 탭, 중간 탭, 마지막 `CAT_MAJ_99`가 실제 클릭·터치 및 키보드로 선택되는지 확인한다.
5. 기존 ARIA 속성, label 연결, `:focus-visible`, 선택 상태를 유지한다.

완료 조건: 모든 활성 조작 요소의 실측값이 `width >= 44 && height >= 44`이며 예외가 0개여야 한다.

### Stage C — 모바일 제주시 카메라 및 렌더링 복구

1. 1440×900에서 390×844로 뷰포트가 변경된 뒤 카메라가 이전 데스크톱 조망을 재사용하는 경로를 재현한다.
2. 지도 컨테이너 리사이즈 완료 후 현재 `gridData` BBOX로 `fitBounds`를 다시 계산한다.
3. 리사이즈 옵저버와 카메라 이동 효과가 중복 실행되지 않도록 단일 경로에서 재맞춤한다.
4. 하드코딩된 제주 중심점·줌으로 우회하지 않고 실제 격자 BBOX를 사용한다.
5. `idle` 이후 다음 수치를 함께 기록한다.
   - API 수신 건수
   - 상태 내 고유 `grid_id` 수
   - 카메라 BBOX 내부 격자 중심 수
   - `queryRenderedFeatures` 개요 레이어 고유 격자 수
   - 카메라 center, zoom, pitch, bearing
6. 업종 테마 전환 후에도 동일한 렌더링 고유 격자 수가 유지되어야 한다.

완료 조건: 모바일 제주시 전체 조망에서 수신 1,351 = 상태 1,351 = BBOX 내부 1,351 = 개요 렌더링 1,351이어야 한다.

### Stage D — 검증 스크립트 판정 로직 교정

1. 각 시나리오에 명시적 assertion을 추가하고 하나라도 불일치하면 프로세스를 실패 종료한다.
2. 렌더링 PASS의 주 판정은 `queryRenderedFeatures`의 고유 `grid_id` 수로 한다.
3. 픽셀 분석은 보조 증빙으로만 사용하며 단독 PASS 조건에서 제거한다.
4. 픽셀 분석을 유지한다면 지도 전체의 단순 RGB가 아니라 레이어 예상 색상, 지도 영역 ROI 및 배경 대조 조건을 적용한다.
5. 모바일 검증 JSON에 다음 항목을 추가한다.
   - 모든 필터·버튼의 CSS px 실측값
   - `innerWidth`, `scrollWidth`, 가로 오버플로 차이
   - 첫·중간·마지막 업종 선택 결과
   - 시도→시군구→연도 선택 결과
   - 실제 터치 팝업 열림 및 뷰포트 내부 여부
   - 키보드 포커스 순서와 포커스 표시 여부
   - `prefers-reduced-motion` 상태 결과
6. FPS는 해당 시점의 렌더링 고유 격자 수와 MapLibre `render` 이벤트 수를 함께 기록한다.
7. 데스크톱 에뮬레이션 결과를 실제 모바일 기기 성능으로 표현하지 않는다.

완료 조건: 고의로 기대 렌더 수를 틀리게 지정했을 때 테스트가 실제로 실패하는 자기검증 1건을 남긴다.

### Stage F — 보고서 정정

1. 기존 보고서는 삭제하지 않고 문서 상단에 정정 상태를 표시한다.
2. 원래 잘못된 판정, 원인, 수정 내용, 수정 전·후 수치를 표로 남긴다.
3. 원시 JSON에 존재하지 않는 비차폐율·오버플로·접근성 수치는 기재하지 않는다.
4. `완벽`, `최우수`, `전수`, `100% 정상`, `실제 모바일 60fps 보장` 같은 과장 표현을 제거한다.
5. 에뮬레이션과 실기기 검증을 명확히 구분한다.
6. 모든 PASS는 원시 JSON의 필드 경로와 캡처 파일을 함께 인용한다.

완료 조건: 보고서 표의 모든 정량값이 원시 JSON에서 동일하게 조회되어야 한다.
